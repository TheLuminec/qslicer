Background

How quantum computing works, and what our slicer does with it

Enough quantum mechanics to read the graphs on this site, followed by the details of the analysis itself. No physics background assumed.

Qubits and superposition

A classical bit is 0 or 1. A qubit holds a pair of complex numbers — amplitudes — one for $|0>$ and one for $|1>$, whose squared magnitudes sum to 1. Writing $\alpha|0> + \beta|1>$ says the qubit will read as 0 with probability $|\alpha|^{2}$ and 1 with probability $|\beta|^{2}$.

The important part is that $\alpha$ and $\beta$ can be negative or complex. That is what lets amplitudes cancel. Every quantum algorithm worth writing is an arrangement for making the wrong answers cancel and the right ones add up, which is also why a phase that looks invisible — it changes no probability on its own — can matter enormously three gates later.

n qubits, 2n amplitudes. Three qubits carry eight amplitudes, one per bit string from 000 to 111. This is why simulating large circuits is expensive, and why a static analysis that never simulates is useful.

Gates

Gates are the instructions. Each one is a reversible rotation applied to one or a few qubits: h spreads a definite state into an even superposition, x flips it, rz turns its phase, cx flips one qubit conditioned on another. Many gates are their own inverse, so applying one twice gets you back where you started — the analyzer uses exactly this to spot uncomputation.

Entanglement

Two qubits are entangled when their joint state cannot be expressed as a product of independent states for the two qubits. In that case, describing each qubit separately does not capture all the correlations in the pair. In the Bell pair above there is no answer to “what is q0 doing?” that does not mention q1. This is the thing that makes quantum slicing hard: a gate on q1 can change how the outcomes of measuring q0 and q1 correlate, even though no instruction names both. Operations on entangled qubits can affect joint measurement statistics and the correlations observed between their outcomes.

Our analyzer approximates this. It maintains groups of qubits: every wire starts in its own group, an entangling gate merges the groups of the qubits it touches, and measuring a qubit closes the group it belonged to. The result is an over-approximation — it can claim entanglement that a full simulation would show has canceled out — which is generally the safer direction for a conservative static analysis to err in.

What creates a group

Any gate in the entangling set: cx, cz, ccx, cswap, rzz among others.

What ends one

A measurement on any member qubit. The analyzer also records gates that look like uncomputation (detected syntactically), but that does not close the group.

Measurement

Measurement produces a classical outcome and changes the quantum state according to the measurement basis. For a projective measurement of a qubit in the computational basis, the post-measurement state is consistent with the observed 0 or 1 outcome. Along with reset, it is one of the only irreversible operations, and it is where a quantum program hands results back to ordinary code — including to if statements that decide which later gates run at all.

Measuring always answers a question in some basis. The default is the Z basis: “is this qubit 0 or 1?” Asking about the X axis instead means applying h first; asking about Y means sdg then h.

What slicing means

A slice is the subset of a program containing only the statements relevant to a particular computation at a particular point. It is defined by a slicing criterion (s, V), where s is a statement and V is the set of variables of interest at that statement — for a quantum program, the qubits and classical bits.

SliceCriterionContains
Static backward SS(s, V) V is used at s Every statement that could affect V at s
Static forward SFS(s, V) V is defined at s Every statement that could be affected by V at s

Both reduce to graph reachability on the QPDG. A backward slice finds the nodes that can reach s along dependency edges; a forward slice finds the nodes reachable from it. That is literally what the slicer does: a graph walk over incoming or outgoing edges, filtered by the dependency types you selected.

The point is not a smaller program but a semantically equivalent one with respect to the criterion. This implementation approximates that goal through a dependency graph, and its guarantees depend on which dependency rules are implemented and enabled. A slice that respected only classical dependencies could look correct and still produce different measurement outcomes — which is why the graph has to carry the quantum-specific edges below.

The dependency types

Classical program analysis has two: control dependence, where whether a statement runs depends on a condition, and data dependence, where a statement reads a value an earlier one wrote. Quantum programs add physical constraints that neither category can express. Ignoring them does not make the analysis imprecise; it makes it wrong.

Qubit data dependence

A qubit's state is described by a pair of complex amplitudes carrying both measurement likelihoods and relative phase, and every gate transforms the whole of it. So a gate's output is a function of the complete state every prior gate on that wire produced.

This is why a gate that looks irrelevant can be essential: z between two Hadamards changes the final probabilities, even though on its own it changes no probability at all.

Implemented and on by default (DataQubitRule).

Measurement dependence

Measurement is not a passive read. It collapses a qubit into a definite classical value, irreversibly and probabilistically, and any later operation conditioned on that outcome depends on the measurement being there.

Slice out the measurement and the conditional branch is severed entirely. Load the teleportation example and keep only these edges to see it isolated.

Implemented and on by default (MeasurementRule).

Entanglement dependence

Once qubits are entangled, an operation on one can change the meaning of a later operation on the other with no classical data flow between them. The dependence holds when the entanglement has not been uncomputed before measurement.

If the entangling operation is undone before the measurement, it and its reversal can both leave the slice. If it is not, the entangling operation and everything that touched those qubits has to stay.

Implemented, ships disabled — an over-approximate rule quickly makes every slice the whole program.

Classical dependence

The ordinary kind, and still needed: classical bits hold measurement outcomes and those outcomes control later operations. Reaching definitions on classical bits are in the default rule set; control dependence on a classical branch is a placeholder rule that emits nothing yet.

Data on by default (DataClassicalRule); control is a stub.

Deliberately out of scope

No-cloning dependence

An unknown quantum state cannot be copied; an attempt to copy entangles instead. cx(0, 1) after x(0) looks like a copy and is not — q1 becomes conditional on q0.

Out of scope: for slicing purposes this is a subset of entanglement dependence and does not need its own edge type.

Temporal dependence

Qubits decohere. A long enough delay between two gates means the second one acts on a qubit that has already lost its quantum information.

Out of scope: coherence time varies by machine, so there is no machine-independent answer to whether a given delay has destroyed the state.

How our slicer works

  1. Parse into an IR

    A parser turns a circuit into a flat list of QuantumInstruction objects, each with a gate name, qubit indices, classical bit indices and parameters. The executing Qiskit parser gets there by running your file and pulling the QuantumCircuit out of the resulting namespace, so what you see in the graph is the circuit after Qiskit has built and composed it — gate names may differ from what you typed. The static interpreters build the same list by reading the file instead (see Four ways in).

  2. Build the QPDG

    Every instruction becomes a node. Then each dependency rule walks the program and emits labeled edges. Rules are independent and pluggable, which is what makes the filter chips on the slicer page meaningful: they select which rules' edges the traversal is allowed to follow.

    DependencyEmitted whenStatus
    Data qubit A gate writes a wire that a later gate reads. Classical def-use, applied per qubit. on by default
    Measurement A later operation is classically conditioned on a measured bit. on by default
    Data classical Reaching definition on a classical bit. on by default
    Control classical Control dependence on a classical branch. placeholder rule
    Entanglement An entangling gate to later operations on the qubits it correlated. implemented, off by default
    Phase A phase-changing gate to later operations that could observe the phase. implemented, off by default

  3. Traverse from a criterion

    A backward slice is a walk along incoming edges from the criterion node, keeping only edges whose dependency type you selected. A forward slice is the same walk along outgoing edges. The criterion node is always included.

  4. Approximate entanglement alongside

    Tracking entanglement exactly would mean carrying an internal representation of the program's quantum state, which is the thing static analysis exists to avoid. The analyzer approximates instead, with a group object per entanglement: a set of qubit indices, the operation that created it, a stack of the operations applied since, an active flag, and the IDs of the groups it was built from.

    Every operation is handled one of three ways:

    • Entangling gate. A new group is created over all the qubits the groups it touches contain, with the gate as its origin. The old groups are marked dormant and recorded as the new group's parents. This happens even when the qubits are already in the same group.
    • Any other gate, not matching the top of the stack. The operation is pushed onto the stack of every active group it touches.
    • Any other gate, matching the top of the stack. The operation is popped and recorded as uncomputed — it canceled the one before it.

    Measuring a qubit deactivates the group it belonged to and opens a new measurement group over the same qubits. The analyzer only reports groups; it does not add edges to the QPDG. Entanglement edges come from the separate entanglement rule, which ships disabled.

    Disentanglement detection is syntactic, not semantic. It catches a self-inverse single-qubit gate applied twice, such as h or x. It misses a repeated cx or ccx, because every entangling gate opens a new group, and it does not detect some equivalent gate sequences that cancel despite using different gates, such as s followed by sdg. Catching those needs state tracking, which is out of scope for the approximation. The two ancilla examples on the slicer page show both sides of this line.

Walkthrough: teleportation

Load Quantum teleportation on the slicer page. The circuit prepares an unknown state on q0, entangles q1 with q2, measures q0 and q1, and then applies corrections to q2 based on those two classical bits.

  1. Slice backward from the final measurement (#10). You get all 11 instructions, and here that is the right answer: the measurement of q2 depends on Bob's corrections, the corrections read the bits Alice's measurements wrote, and those measurements depend on everything done to q0 and q1. Teleportation really does need the whole circuit.
  2. Now turn off every dependency except Measurement. Slice backward from #10 again and the slice collapses to {10} alone. The final measurement is not classically conditioned on anything, so no measurement edge reaches it.
  3. Slice backward from the first correction (#8) with only Measurement on. Now you get {7, 8}: the if_else block and the measurement of q1, which wrote the c1 bit it reads. That is what the measurement rule exists to produce, and no data-qubit edge would ever have found it — the correction is on q2, the measurement is on q1. The second correction (#9) reads c0 instead, and slicing from it gives {6, 9}.
  4. Open the entanglement tab. Group 3 forms at the Bell-pair cx (#3) over q1 and q2, group 4 absorbs q0 at Alice's cx (#4), and the mid-circuit measurements (#6 and #7) close group 4 and open measurement group 5.
  5. Slice forward from the Bell-pair cx (#3). Everything from there to the end lights up — eight of the eleven instructions. In a teleportation circuit, that is most of the program.

Four ways in

The analysis is the same whichever you pick — every front end produces the same instruction list, and everything downstream works on that. What differs is what has to happen to your file first, so which one runs is an explicit choice: the Interpreter dropdown on the slicer page. Loading an example or uploading a file sets it for you; nothing else moves it.

Python (.py)

Qiskit (Python) has to execute your file, because the QuantumCircuit only exists once the code that builds it has run. The circuit you see is therefore the circuit Qiskit actually built, after any composition and transpilation — which is why gate names sometimes differ from what you typed. On this site that execution happens in a separate worker process under a timeout, so a circuit that loops forever kills a worker rather than the server. That bounds accidents; it is not a sandbox.

Qiskit (Python, static) reads the same file without running it: a small interpreter of its own follows the Python and the Qiskit calls that build the circuit, and links every instruction back to its source line. Anything only a real run could decide stops it with the line number, and the executing interpreter is the way past.

OpenQASM (.qasm)

OpenQASM 3 is parsed as text against the OpenQASM grammar, through Qiskit. OpenQASM 2/3 (static) interprets the file without Qiskit and, like the static Python route, keeps each instruction's source line. Either way nothing in the file is executed, so there is nothing to time out and nothing to contain — this is the route to prefer for a circuit that did not come from you.

Export one from any Qiskit circuit with qiskit.qasm3.dumps(qc). The quick checks and LintQ are skipped, since they read a Python syntax tree; the dependence checks still run.

Tools we use

Qiskit
IBM's quantum SDK. The framework used to implement most of our sample circuits, and the library that provides the QuantumCircuit objects consumed by the parser. How Qiskit builds and decomposes library circuits is also why parsed gate names sometimes differ from the source.
OpenQASM
A textual assembly language for circuits, and the execution-free way into this tool. One parser loads it through qiskit.qasm3.load and another interprets it without Qiskit; either way the file is read rather than run.
NetworkX
Graph library. The QPDG is a MultiDiGraph — multi, because two instructions can be joined by several dependencies of different kinds at once.
Matplotlib
Draws the desktop visualizers in scripts/visualizer.py and scripts/combined_visualizer.py.
Flask
Serves this site and exposes the analysis over a small JSON API.
Static checks
Linters that read your file without running it, before the Qiskit parser executes anything. The quick checks flag common Qiskit mistakes from the syntax tree and are on by default. LintQ (Paltenghi and Pradel, FSE 2024) comes as a port that matches the original's warnings and, where CodeQL is installed, as the original queries. The dependence checks read the QPDG for gates no measured bit depends on, and are the only ones that also read OpenQASM. Pick them under Lint on the slicer page; the Benchmark page grades the same selection on the Bugs4Q bugs.

Gate reference

Reference for the gates documented in the slicer page's hover cards. Entangling gates can create entanglement between the qubits they act on; phase gates are diagonal in the computational basis, so they change only relative phases; self-inverse gates undo themselves when applied twice. Multi-qubit matrices use Qiskit's qubit ordering: the first qubit argument is the least significant bit, so for cx(0, 1) the rows run |q_{1}q_{0}> = |00>, |01>, |10>, |11>.
