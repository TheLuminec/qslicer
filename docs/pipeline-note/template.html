How the Quantum Slicer slices and lints a program

The tool reads a Qiskit or OpenQASM program without running it, rebuilds its circuit as a flat list of instructions that each know their source line, connects them in a Quantum Dependence Graph, and answers slicing questions as graph reachability. The same static reading feeds pluggable linters, whose findings are drawn back onto the graph. This note follows each stage as the code implements it, and every number in the worked example and the benchmark comes from running the code at this commit.

1The pipeline at a glance

Figure 1 shows the three paths through the system. The analysis path turns source text into an intermediate representation (IR), builds the dependence graph and serves slices. The lint path runs first, on its own static parse, and its findings are joined to the graph at the end. The benchmark path runs the same linters over pairs of buggy and fixed programs and grades them against the fix.

Everything after the IR is independent of the source language. Neither front end imports, evaluates or executes the submitted program, and the web API refuses the old route that did (language="qiskit", "python" or "py" returns execution_disabled).

The request's language picks the front end: qiskit-static (or static) for Python and qasm-static (or openqasm-static) for OpenQASM 2 and 3. These are the two choices the page offers. An API caller that sends no language gets the front end the file extension suggests (.qasm and .qasm3 for OpenQASM). The names qasm, openqasm and qasm3 still reach an older route through qiskit.qasm3.load. It executes nothing either, but it reads only OpenQASM 3 and keeps no source locations; this note does not cover it further.

2Front ends: rebuilding the circuit without running it

Both front ends are interpreters over a syntax tree. They differ in where the tree comes from and what language they interpret, and they share everything from the circuit model onward.

2.1 Qiskit (Python)

StaticQiskitParser.parse() calls ast.parse, then runs _Interpreter, a tree-walking evaluator that dispatches each statement to _exec_<Node> and each expression to _eval_<Node>. It evaluates over a value domain it controls completely: plain Python data; its own model of Qiskit objects (StaticCircuit, StaticRegister, StaticBit, StaticGate); Symbol for parameters and arithmetic over them; _ModuleRef for an import, which is recorded and never performed; _Native for the built-ins and library functions it implements itself; and Unknown for anything only a real run could produce.

Unknown carries only the source text it stands for. Every operation that needs a concrete value raises internally, and the enclosing expression becomes another Unknown. That is why a script that simulates and plots its circuit still parses: the results half turns into unknowns. An unknown only stops the parse where the circuit needs it:

Where an Unknown landsOutcome
A gate parameterKept as a symbolic Symbol, with a warning. Parameters create no dependencies.
A qubit or clbit index, register or circuit sizeStaticParseError with the line.
The condition of a loop or if whose body cannot touch a circuitThe block is skipped, names it would assign become Unknown, and a QS200 warning is shown.
The condition of a loop or if whose body can touch a circuitStaticParseError with the line.

Python for, while and if statements run concretely, so loops are unrolled and helper functions are followed; the call line of every file-defined function is pushed onto a via stack. Qiskit calls go through call_method and circuit_method to modelled handlers, and every instruction is placed through place(), which applies Qiskit's argument broadcasting. The interpreter refuses eval, exec, compile and any attribute starting with _, and bounds its own work: 2,000,000 statements and loop iterations, 200,000 instructions, call depth 40, 1,000,000 elements in any collection it builds, 100,000 bits per register, and a wall-clock limit (20 s for the analysis, 5 s for linting).

A script may build several circuits. _choose_circuit takes the module-level StaticCircuit with the most top-level instructions (an if_else counts as one), the same rule as the older executing parser. On a tie, the circuit defined first wins; calls such as execute or transpile play no part, since unmodelled calls return Unknown.

2.2 OpenQASM 2 and 3

StaticOpenQASMParser takes its syntax from the OpenQASM project's ANTLR reference parser (openqasm3.parse), so syntax coverage tracks the specification and every statement carries a span. Its own _QasmInterpreter supplies the meaning. for loops are unrolled and subroutines inlined, with the call line added to via. A branch whose condition is known at compile time is simply taken. A branch on measured bits becomes one if_else, switch_case or while_loop instruction, shaped as Qiskit builds it, that lists the clbits its condition reads. A run-time value copied into bits becomes a store instruction that reads the source bits, so a dependency survives the copy. It always builds exactly one circuit.

OpenQASM 2 goes through the same grammar and interpreter. The OpenQASM 3 grammar already accepts qreg, creg and measure q -> c, and the interpreter knows the gates of qelib1.inc as well as stdgates.inc. The one OpenQASM 2 statement the grammar lacks, opaque, is rewritten to an empty gate before parsing when the header says OPENQASM 2, so an opaque gate stays one instruction, as in Qiskit.

2.3 One circuit model, one lowering

The model is shared in code, not just in spirit: the OpenQASM parser imports StaticCircuit, StaticInstruction, broadcast and circuit_to_program from the Qiskit parser's module. circuit_to_program(circuit, frontend) is the only way into the IR. It maps every bit object to a flat integer index, turns an instruction's condition_bits into metadata["condition_clbits"], and passes the source location through.

3The intermediate representation

A QuantumProgram is a register size pair and an ordered list of instructions. Each QuantumInstruction has a name, integer qubits and clbits, params, metadata and a location. A SourceLocation holds start and end line and column and a via tuple of call-site lines, outermost first. The web app turns it into a node's line and source span, which is what links the graph and the editor in both directions.

Three properties of the IR matter for everything downstream:

  • It is flat and unrolled. A loop body that runs k times yields k instructions sharing one source span, so each iteration is its own graph node.
  • Control flow on run-time values is one opaque node. An if_else keeps its bodies as circuit objects inside params; its qubits are the qubits its bodies use, and its clbits list the condition's bits first. The dependence rules never look inside a body.
  • Classical conditions are explicit. metadata["condition_clbits"] is the only thing the classical rules read.

4Building the Quantum Dependence Graph

QDG(program, rules) adds one node per instruction, keyed by its index, then lets each rule make one pass over the program in order. Every rule that emits edges keeps a single "last writer" map from a wire to the index of the instruction that last touched it. Writing Q(i) for the qubits of instruction i, C(i) for its clbits and R(i) for its condition clbits, the three active rules produce:

DATA_QUBITu → v  iff  ∃ q ∈ Q(v) : u = max { w < v : q ∈ Q(w) }
MEASUREMENTu → v  iff  ∃ c ∈ R(v) : u = max { w < v : w is a measurement ∧ c ∈ C(w) }
DATA_CLASSICALu → v  iff  ∃ c ∈ R(v) : u = max { w < v : c ∈ C(w) }

Several properties follow directly from this construction.

  • The QDG is a DAG in program order. Every edge goes from a lower index to a higher one, so program order is a topological order.
  • Construction is linear. Each rule does constant work per operand, so a program with n instructions and at most k operands each yields at most nk edges per rule.
  • Edges are typed and attributed. The graph is a networkx.MultiDiGraph; each edge carries dependency and rule. Parallel edges are expected. Whenever the last writer of a condition bit is a measurement, the MEASUREMENT edge duplicates the DATA_CLASSICAL edge from it (n6→n7 in Figure 2), and edge counts include both. A gate whose qubits share a last writer gets one DATA_QUBIT edge per shared qubit.
  • The approximation errs toward larger slices. Every qubit operand counts as both a use and a definition, so a control qubit, a barrier and a measurement all become writers of their wires. An if_else lists its condition bits among its clbits, so it also becomes the last writer of those bits for DATA_CLASSICAL. Both choices add edges and never remove one.
  • A new dependency type needs only a new rule class. The slicer filters on whatever types the edges carry, and the web app builds its Follow chips from the rules that ran, with each type's edge count.

5Slicing as reachability

A slicing criterion is SlicingCriterion(node_idx, dep_types). For a criterion s and a set of allowed types T (all types when dep_types is None):

backwardBST(s) = { u : there is a path u = v0 → v1 → … → vk = s with every edge's type in T }
forwardFST(s) = { v : there is a path s = v0 → … → vk = v with every edge's type in T }

Both sets contain s (k = 0). QuantumSlicer computes them with a worklist over in-edges or out-edges, skipping an edge whose type is not in T, in O(V + E). The type filter applies to every edge on the path, so it removes whole routes, not single nodes: following only DATA_QUBIT edges answers "what reaches this gate through its qubits alone", and adding MEASUREMENT answers "and through the classical outcomes it is conditioned on".

The browser sends the Follow chips' selection as dep_types to /api/slice, which runs this slicer on the QDG cached under the analysis token. Qubit-wise (horizontal) slices are computed in the browser; SlicingCriterion.qubits is reserved and not yet read by the slicer.

7The lint path

Linters are registered in webapp/linters.py as Linter records: an id, a list of rules, a run(context) function, the languages it reads, whether it is on by default, an available() check for external tools, and an optional batch mode. Only the quick checks are built into linters.py. The other three linters are add-ons: the dependence checks in webapp/linter_plugins/dependence_checks.py, and the LintQ port and its CodeQL counterpart in linter_plugins/lintq.py. On first use the registry imports every module in webapp/linter_plugins/, and any named in the QSLICER_LINTER_PLUGINS variable, and registers the LINTER or LINTERS each defines. A module that fails to import is reported and skipped rather than taking the site down.

A request selects rules by id (quick/QS002, or a bare dependence for all of a linter's rules). linters.run groups the selection by linter, skips linters that do not read the language or are unavailable, and calls each with one shared LintContext. The context parses the source with the same static front end at most once, lazily, through its own linters._static_parse under a 5 s limit, and hands out either the program or the failure. A linter that raises becomes one <ID>-CRASH error finding. tag() then keeps only the selected codes and stamps each finding with tool and rule, and the list is sorted by line. Every finding has the same shape: code, severity, line, column, message, hint, plus nodes, lines or qubits where the linter knows them.

7.1 Four linters, four sources of evidence

  • Quick checks (webapp/lint.py, on, Python only) report what Python or Qiskit would raise. One ast.NodeVisitor pass collects circuits with literal sizes, method calls and attribute reads, and the checks compare literal indices against literal sizes. QS005, QS012 and QS013 look names, methods and keyword arguments up in the installed Qiskit by import and introspection; the submitted file itself is never imported. QS014 reads the lint context's parse failure: the static parser raises Qiskit's CircuitError where Qiskit would, at the line inside a helper or loop iteration, so QS014 catches computed indices that the literal checks cannot see.
  • Dependence checks (webapp/linter_plugins/dependence_checks.py, on, Python and OpenQASM) read the rebuilt program. They see only programs the static front end can rebuild, which on Bugs4Q is {{B_READ}} of {{B_PROGRAMS}}. QD01 builds a QDG with the request's profile and reports every gate outside the union of the backward slices of all instructions that write a classical bit. QD05 follows the set of qubits provably still in |0⟩ through diagonal gates and measurements; QD10 follows each qubit's Pauli eigenstate through single-qubit Clifford gates. Findings name the node indices they mean, and findings with the same code and line are merged with a count, so a loop is reported once and marks every iteration.
  • LintQ port (scripts/Linters/lintq_port.py, off by default) reimplements LintQ's ten CodeQL queries on Python's syntax tree. It builds per-scope control-flow graphs, reaching definitions and API paths that mirror LintQ's CodeQL library, and deliberately keeps that library's limits. Its conformance test (tests/lintq/) checks that it gives the original's warnings line for line on 239 files: LintQ's 35 test programs, 4 probe programs written for the queries' edge cases, the 22 bundled examples and the 178 Python files under benchmarks/bugs4q/programs/. That corpus yields 190 warnings; Table 3's combined total of 190 on Bugs4Q is a coincidence.
  • LintQ original (scripts/Linters/codeql_lintq.py, off, needs CodeQL) runs the authors' queries through the CodeQL CLI and reads the SARIF output. It is slow to start, so the benchmark uses its batch mode.

7.2 Where the slicer and the linter meet

QD01 is the slicer used as a checker. Let W be the instructions of the rebuilt program that write a classical bit: measurements, store copies, and control-flow blocks whose body writes one. The live set is L = ⋃w ∈ W BS(w), and every gate outside L is reported. Blocks are the subtle case. A block lists only its condition bits among its clbits, so QD01 looks into its body to see whether it writes. Because the QDG over-approximates dependence (Section 4), a gate outside L has no dependence path to any bit the program writes, so removing it cannot change the program's classical output. The argument covers only that output. A program read through its statevector has no writers, so QD01 does not run on a circuit that never measures (QD06 reports that case). The check reports dead gates rather than pruning them; it is a likely mistake, not an optimisation.

7.3 From findings back to nodes

The linters parse the source themselves, so their node indices are checked before the graph uses them. attach_lint_nodes keeps a finding's named nodes if at least one of them comes from the finding's line in the main parse; otherwise it marks every node whose source span covers the finding's lines (or line), which is the same lookup as clicking a line number in the editor. This is how a finding inside a loop marks every unrolled iteration, and how a QS finding, which has no node indices, still lights up the gates on its line.

8One request, end to end

Figure 3 orders the calls inside /api/analyze and a following /api/slice. Two design choices show up here. First, the program is parsed twice: once inside the lint context (5 s) and once for the analysis (20 s). Linting runs first because its findings are what explain a failed parse, QS014 needs the failure itself, and a syntax error (QS000, when selected) stops the request before the main parse is attempted. Without QS000 the main parse reports the error itself: the Python front end as a static_error with its line, the OpenQASM one as a qasm_error. The quick checks read only Python, so on OpenQASM with quick rules selected the response carries a QS100 note saying they did not run. Second, slicing never re-parses: the QDG and program are cached in process memory under a token derived from the file name, profile, front end and source, in an LRU of 24 entries. That cache is why the deployment runs one worker process with several threads; a second worker would not recognise the first one's tokens.

9Benchmarking the linters

A dataset is any folder under benchmarks/ with a manifest.json listing pairs of buggy and fixed programs; the first is the 62 Qiskit bugs of Bugs4Q, vendored at commit bb853b8. Ground truth comes from the fix: ground_truth diffs the two programs with difflib.SequenceMatcher on whitespace-stripped lines, and the fault lines are the buggy program's code lines that the fix deletes or rewrites. A fix that changes more than half the code lines is a rewrite and is reported separately, since any warning in it lands on a fault line; a fix that only adds code is an omission, and the code lines on either side stand in. A pair whose code lines do not differ at all (a fix in comments or whitespace) is kind none and is not graded. Of the {{B_BUGS}} fixes, {{B_EDITS}} are edits, {{B_REWRITES}} rewrites and {{B_OMISSIONS}} omissions; none is of kind none.

Each bug is graded per rule set by three nested tests (Figure 4). Detected is the headline: a warning on a fault line whose rule fires fewer times on the fixed program, so the fix is what silenced it. Rewrites flatter every measure, since nearly every line of a rewritten program is a fault line. The figure to quote is therefore the one without them: {{B_DETECTED_NR}} of {{B_NR}} bugs detected, at {{B_PREC_NR}} warning precision rather than {{B_PREC}}. Nothing is executed; the linters see exactly what they see on the slicer page.

10Limitations and documentation

10.1 Limitations of the current pipeline

  • Classical control dependence is a placeholder. ControlClassicalRule emits nothing, and an if_else is one node whose bodies the rules do not enter.
  • Entanglement and phase rules ship disabled, and only the baseline profile exists, so there is no per-analysis toggle. Slices do not yet exclude an entangling gate that is uncomputed before the criterion; the entanglement analyzer's groups are shown in a side panel but do not feed the slicer.
  • Static reading has edges. Classes defined in the file, transpile and pass managers are not followed, and control flow that depends on an unknown value and touches a circuit is refused with its line rather than guessed.
  • Scale. Unrolling makes the IR large (the static parsing notes estimate about 156,000 nodes for a 4,000-layer, 20-qubit ansatz). Because every rule keeps one last-writer state per wire, the notes propose chunking along source structure, summarising each chunk at its qubit and clbit boundary; this would be exact for the current rules but is not implemented.
  • Quick checks read only Python, and the dependence checks need a circuit the static parser can rebuild.

10.2 Documentation

While this note was written, the README and the project wiki had drifted from the code in four places. They were brought in line on 3 Nov 2026:

  • Both READMEs now list the dependence checks as QD01–QD03 and QD05–QD10. QD04 became QS014 in the 2026-10-29 reorganisation.
  • wiki/Research/Linting.md now describes the current design. The dependence checks are a plugin in webapp/linter_plugins/, the LintQ port works on the syntax tree and keeps the original's limits, and the rule tables match the registry.
  • wiki/Research/Static-Parsing.md now lists the OpenQASM features the interpreter supports (run-time while, switch, box, physical qubits, extern) and what it still refuses.
  • wiki/Research/Bugs4Q-Benchmark.md now reports the current run: {{B_DETECTED}} of {{B_BUGS}} bugs detected, {{B_READ}} of {{B_PROGRAMS}} programs read.

A review of this note also found a bug in QD01 itself. It counted only measure instructions as outputs, so it reported an if_test block that measures inside, and an OpenQASM store after the last measurement, as dead. Every instruction that writes a classical bit now counts as an output (Section 7.2), with regression tests for both cases.

The graph is called the QDG throughout, as in scripts/qdg.py. "QPDG" now appears only where a page cites the IEEE paper that introduced it.
